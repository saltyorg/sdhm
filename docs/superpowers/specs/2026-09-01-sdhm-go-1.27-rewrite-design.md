# SDHM Go 1.27 Rewrite Design

Date: 2026-09-01
Status: Approved in conversation; pending written-spec review

## Purpose

Replace the existing daemon implementation with a smaller, testable Go 1.27 design that treats Docker discovery as an authoritative snapshot, treats `/etc/hosts` mutation as a recoverable transaction, and gives one coordinator ownership of scheduling and shutdown.

The rewrite preserves the Saltbox deployment contract while correctly supporting every network supplied through the existing comma-separated `--networks` option. One resolved default network owns bare aliases; all other networks use qualified aliases.

## Goals

- Upgrade the module and CI toolchain floor to Go 1.27.0.
- Replace the current multi-goroutine updater coordination with one event-loop coordinator.
- Never update the managed hosts section from a partial Docker snapshot.
- Make every hosts-file replacement atomic on the destination filesystem and durable across a successful return.
- Restore a corrupt managed section only from a strictly validated backup; otherwise fail closed.
- Report health from current active conditions, while retaining bounded diagnostic history.
- Reconcile one complete snapshot across all configured Docker networks.
- Preserve current Saltbox names while preventing bare-alias collisions on additional networks.
- Make CLI, Docker, hosts, daemon, and health behavior independently testable.
- Preserve the existing hosts-section format and compatible command behavior unless this design explicitly changes it.
- Qualify the finished daemon against a real Docker `saltbox` network and a disposable secondary network in a Saltbox VM.

## Non-goals

- Dynamic configuration reload.
- A plugin system or generic storage framework.
- Supporting operating systems other than Linux.
- Replacing Cobra, the Moby client, or GitHub Actions.
- Adding a third-party linter solely to increase tool count.

## Compatibility Contract

The following behavior remains stable:

- The binary remains `sdhm`.
- `--networks/-n` remains the primary comma-separated network option and defaults to `saltbox`.
- The default hosts file remains `/etc/hosts` and backup remains `/etc/hosts.backup`.
- Managed content remains between `# BEGIN <section>` and `# END <section>` lines.
- Existing interval, health address/port, hosts path, backup path, section name, and debounce options remain available.
- The health endpoint remains `/health` and retains the existing top-level JSON keys and error-record fields.
- Version data remains injected at build time, and `sdhm --version` remains exactly `sdhm version <version>`.
- Release artifacts remain named `sdhm_linux_<architecture>` so historical Saltbox installers continue to download them.

The following behavior changes intentionally:

- `--default-network` optionally selects which monitored network also receives bare aliases.
- Without an explicit default, `saltbox` wins when monitored; otherwise the first configured network wins.
- Durations accepted by `time.ParseDuration`, including milliseconds and compound durations, are valid; an exact positive integer with a `d` suffix remains supported.
- Invalid configuration returns one concise error without printing full command usage.
- Marker corruption triggers validated backup recovery instead of unconditional manual regeneration.
- Health becomes healthy only after the failing concern succeeds; errors no longer age into recovery without evidence.

### Historical Saltbox deployment contract

Every Saltbox revision since the Go binary was introduced in November 2025 invokes SDHM with `--networks <comma-list> --interval <duration> --health-port <port>`. Older revisions use different allocated port values but the same flag contract. They also parse the third whitespace-delimited token from `sdhm --version`. The rewrite therefore requires no Saltbox repository change and remains installable by older Saltbox checkouts that always fetch the newest SDHM release.

## Package Structure

```text
cmd/sdhm/
  main.go          signal context, command execution, and exit status
  run.go           production dependency wiring

command/
  root.go          Cobra factories, flags, parsing, and validation

daemon/
  daemon.go        public coordinator construction and lifecycle
  loop.go          event-loop scheduling and state transitions
  types.go         endpoint, event, timing, and consumed interfaces

docker/
  client.go        Moby adapter for snapshots and event streams

hosts/
  markers.go       exact marker parsing and managed-section replacement
  render.go        deterministic endpoint rendering
  store.go         transactional file storage, backup, and recovery

health/
  tracker.go       active conditions and bounded history
  handler.go       compatible JSON rendering
  server.go        timeout-configured HTTP lifecycle
```

The old `internal/config`, `internal/debounce`, `internal/logger`, `internal/timeutil`, and `internal/updater` packages are removed after cutover. The old Docker and hosts implementations are replaced rather than wrapped. Structured logging uses `log/slog` directly.

## Module Interfaces

The `daemon` package defines the interfaces it consumes:

```go
type Endpoint struct {
    Network string
    IP      netip.Addr
    Aliases []string
}

type Event struct {
    Action      string
    ContainerID string
    Network     string
}

type NetworkSource interface {
    Ping(context.Context) error
    Snapshot(context.Context, []string) ([]Endpoint, error)
    Events(context.Context, []string) (<-chan Event, <-chan error)
    Close() error
}

type HostStore interface {
    Prepare(context.Context) error
    Apply(context.Context, []Endpoint) error
}

type HealthServer interface {
    Start() error
    Done() <-chan struct{}
    Err() error
    Shutdown(context.Context) error
}
```

Production Docker and hosts adapters import `daemon` and satisfy these interfaces. The daemon does not import either adapter. `cmd/sdhm/run.go` is the wiring point.

`HostStore.Apply` is deliberately deep. It owns marker validation, rendering, no-change detection, backup creation, replacement, durability, validation, and rollback. The daemon only decides when to call it.

The production hosts store receives the resolved default network at construction. Rendering contains no hard-coded Saltbox branch: it applies the default-network naming rule to endpoint data supplied by Docker.

The health tracker is a concrete concurrency-safe module because daemon and handler tests both use the real implementation. The HTTP server is consumed through `HealthServer` so daemon shutdown tests do not bind real ports.

`HealthServer.Start` may be called once; it binds synchronously and, on success, starts exactly one serve goroutine. `Done` closes exactly once when that goroutine exits. `Err` is read only after `Done` closes and returns `nil` for normal `http.ErrServerClosed` shutdown. `Shutdown` is idempotent, calls `http.Server.Shutdown`, waits for the serve goroutine before returning, and reports only shutdown or wait errors; the terminal serve result is reported exclusively by `Err`. The daemon alone calls `Start` and `Shutdown`; the health module owns the listener and serve goroutine.

## Configuration

The validated runtime configuration contains a normalized network list, one resolved default network, and positive durations:

- Networks: split the existing comma syntax, trim surrounding space, discard empty items as the current CLI does, reject whitespace/control/comment delimiters inside a retained name, remove duplicates, preserve first occurrence order, and require at least one result. The CLI default is `saltbox`.
- Default network: trim an explicitly supplied `--default-network` and require an exact match in the normalized configured list. When omitted, resolve to `saltbox` if present, otherwise the first configured network.
- Periodic interval: positive.
- Debounce delay: positive.
- Maximum debounce delay: greater than or equal to debounce delay.
- Health port: 1 through 65535.
- Health address: non-empty and accepted by `net.Listen`.
- Hosts and backup paths: non-empty, cleaned, and not the same path.
- Section name: non-empty, single-line, and unable to inject complete marker lines.

Raw strings are parsed only in `command`. Internal modules receive typed, validated values.
`daemon.New` defensively revalidates every retained network name and rejects
whitespace, control runes, and `#` before accepting the typed configuration.

## Startup and Reconciliation

Startup is ordered so every acquired resource has a defined cleanup path:

1. Construct the production adapters from validated configuration.
2. Ping Docker with a fixed ten-second child context. Failure aborts startup so the process supervisor can retry.
3. Bind the health listener synchronously. Failure aborts startup and closes Docker.
4. Run `HostStore.Prepare`. Failure closes the listener and Docker without starting background work.
5. Attempt the first authoritative reconciliation.
6. If the initial reconciliation fails after a successful ping, retain the valid current hosts file, publish a degraded condition, schedule reconciliation retry, and enter the event loop.

Reconciliation consists only of `NetworkSource.Snapshot` for the complete configured network list followed by `HostStore.Apply`. Each snapshot receives a fixed ten-second child context; this timeout is internal and is not a CLI option. `Apply` receives the daemon context and is never called when `Snapshot` returns an error. A successful combined snapshot clears the Docker snapshot condition; a successful apply clears the hosts update condition and resets reconciliation backoff.

## Docker Snapshot Semantics

`Snapshot(ctx, networks)` returns a complete view of running containers attached to any configured network or an error. It never returns a knowingly partial successful result.

1. Call `ContainerList` once with `All: false` and `client.Filters{}.Add("network", networks...)`. This creates one `network` filter key with a distinct value for each normalized name; never join the names into one comma-containing Docker filter value. Docker ORs the separate values within that term.
2. Treat any list error as a snapshot error and retain the current hosts file.
3. Inspect each returned container exactly once. Docker 29.7.2 list responses were verified to return endpoint IPs while leaving both `Aliases` and `DNSNames` null; inspect is required to preserve Saltbox's configured aliases.
4. If inspect reports Docker's canonical not-found condition, treat it as a list/inspect removal race and skip that container.
5. For every other inspect error, return an error and discard the whole combined snapshot.
6. For each configured network, read the inspected endpoint when present. Absence means the container disconnected between list and inspect and is skipped for that network.
7. For every present endpoint, require a valid IPv4 address or valid global IPv6 fallback plus at least one non-empty value from `Aliases`. Do not use `DNSNames`, which would add container IDs and other names absent from current Saltbox hosts files.
8. Normalize aliases by removing empty values and duplicates, then emit one `Endpoint` per matching container/network pair.
9. Sort endpoints and aliases deterministically before returning.

A configured network with no running containers is a valid empty contribution to the combined snapshot. Any malformed present endpoint aborts the whole snapshot so one failing network cannot delete otherwise valid entries.

The event stream uses `client.Filters{}.Add("type", "network").Add("event", "connect", "disconnect").Add("network", networks...)`, again transmitting each network as a separate value. Each mapped event includes the actor's network name. An event on any monitored network triggers reconciliation of the entire combined snapshot. Event handling does not inspect containers merely to improve log messages.

## Hosts Parsing and Rendering

Markers are recognized only when an entire logical line equals the configured begin or end marker after trimming carriage return from CRLF input. Marker-like substrings in comments or hostnames are ordinary content.

A valid managed section has exactly one begin marker, exactly one end marker, and the begin marker precedes the end marker. Missing one marker, duplicates, or reversed order are corruption.

Rendering is deterministic:

- Invalid IP addresses and empty alias sets are rejected before file mutation.
- Aliases containing whitespace, control bytes, or hosts-file comment delimiters are rejected before file mutation.
- On the resolved default network, each raw alias expands to both the bare hostname and `<alias>.<network>`.
- On every other network, each raw alias expands only to `<alias>.<network>`.
- Duplicate expanded hostnames within an endpoint are removed.
- Endpoints are sorted by first hostname, then network, then IP.
- IP columns remain aligned as in the existing output by padding each rendered
  address to the maximum rendered IP width before the hostname column.
- `replaceManagedSection` preserves byte-for-byte everything outside the
  managed body, including both marker lines and the entire suffix from the END
  marker onward. It never normalizes user-owned EOF whitespace.
- The rendered managed body has one newline per entry; it does not impose a
  whole-file trailing-newline rule.

`Apply` always renders the complete desired section. If the bytes match the current file, it returns successfully without changing the target or backup.

## Transactional File Storage

The store rejects symlink and non-regular targets. It checks context cancellation before every mutation phase, while acknowledging that individual filesystem syscalls are not interruptible.

`Prepare` requires the target to exist; a missing system hosts file is a fatal configuration or host-state error. The explicit `regenerate` command may create a missing target.

Metadata extracted from an existing regular file preserves its permission bits plus `ModeSetuid`, `ModeSetgid`, and `ModeSticky`, along with UID and GID. A newly created regeneration backup is always mode `0644` and owned by the current process UID/GID; replacing any existing backup preserves that backup's extracted metadata.

The package has one narrow private fault-injection seam rather than a general filesystem abstraction:

```go
type syncFile interface {
    io.Writer
    Name() string
    Chmod(fs.FileMode) error
    Chown(int, int) error
    Sync() error
    Close() error
}

type syncDir interface {
    Sync() error
    Close() error
}

type fileOps interface {
    Lstat(string) (fs.FileInfo, error)
    ReadFile(string) ([]byte, error)
    CreateTemp(string, string) (syncFile, error)
    Rename(string, string) error
    Remove(string) error
    OpenDir(string) (syncDir, error)
}
```

The production implementation delegates directly to `os`. Hosts tests wrap it to fail one named operation deterministically, including write, file sync, close, rename, directory open/sync, readback, chmod, and chown. This seam remains private to `hosts`; callers still see the deep `HostStore` interface.

The private `replaceFile` primitive only replaces one path. It never reads or changes the configured backup as a side effect. It returns whether rename occurred so its caller knows whether rollback is required after a late failure.

For an existing valid target, replacement follows this sequence:

1. Read and validate the current target.
2. Render and validate the complete proposed bytes in memory.
3. Retain the validated current bytes in memory and atomically replace the backup with those bytes through `replaceFile`.
4. Atomically replace the target with the proposed bytes through `replaceFile`.
5. If target replacement fails before rename, return the error with the original target unchanged.
6. If target replacement fails after rename, derive a rollback context with `context.WithTimeout(context.WithoutCancel(ctx), 5*time.Second)` and call `restoreTarget` with the retained validated current bytes. Caller cancellation remains in the primary error but cannot prevent the bounded rollback attempt.

`replaceFile` creates its temporary file in the destination parent, applies ownership, writes, applies the complete final mode, syncs, closes, renames without a cross-device fallback, syncs the parent directory, and reads back the destination for exact comparison. Final mode is applied after both chown and write because either operation may clear setuid or setgid bits. Errors before rename report `renamed=false`; rename and every later failure report `renamed=true`.

Before rename, every exit attempts to close and remove the temporary file. Cleanup failures are joined with the primary error. After rename, the old temporary path no longer exists and no removal is attempted. Directory-handle close errors are checked and joined as well.

`restoreTarget` invokes `replaceFile` only for the target path. It never refreshes, deletes, or otherwise mutates the backup. It does not recursively attempt another rollback. Late-failure callers give it the bounded rollback context described above; direct preparation recovery continues to use its caller context. A restore that reaches rename but fails directory sync or readback still returns an error because durability was not proven.

If the primary operation and rollback both fail, return `errors.Join(primary, rollback)` so neither failure is hidden.

Backup replacement uses the same adjacent-temporary-file, sync, rename, and parent-sync guarantees in the backup directory.

## Preparation and Recovery

`Prepare` handles three states:

1. **Valid section:** leave the target unchanged; if the backup is missing or invalid, seed it transactionally from the valid target.
2. **No markers:** treat the surrounding hosts file as valid unmanaged content, append an empty managed section transactionally, then ensure the backup contains the resulting valid file.
3. **Corrupt section:** read the backup, require exactly one valid ordered marker pair, and restore it transactionally. If the backup is missing or invalid, return an error without changing the target.

Automatic recovery never overwrites a known-valid backup with corrupt target bytes.

The explicit `regenerate` command creates Ubuntu-compatible fresh content with the current hostname. If the prior target is valid, it becomes the backup before replacement. If it is corrupt, the existing valid backup is left untouched. After regeneration, a missing or invalid backup is replaced with the new valid file so automatic recovery remains available. A missing backup created by regeneration uses mode `0644` and current-process ownership independently of target metadata; an existing invalid backup retains its own metadata when its content is replaced.

## Coordinator Event Loop

One goroutine owns scheduling state:

- Periodic timer
- Debounce timer
- Maximum debounce timer
- Event-stream reconnect timer
- Event-stream stability timer
- Reconciliation retry timer
- Pending reconciliation flag
- Shutdown transition

The Moby client supplies event and error channels, but no application callback starts a reconciliation.

### Event behavior

- The first relevant event starts both debounce and maximum-delay timers.
- Each later event resets only the debounce timer.
- Whichever timer fires first requests one reconciliation.
- Events observed after a request is pending remain coalesced into that request.
- Events that become readable after a reconciliation cause at most one following debounced reconciliation.
- A periodic timer requests immediate reconciliation and resets after the attempt.
- A failed reconciliation starts a cancelable retry backoff from one second to a maximum of thirty seconds.
- A successful reconciliation stops the retry timer and resets reconciliation backoff to one second.
- Any periodic or event-driven trigger that arrives before a scheduled retry may start the next attempt earlier; beginning an attempt always stops the old retry timer.
- Beginning any attempt stops and drains periodic, debounce, maximum-delay, and retry timers. The periodic timer resets after the completed attempt, so simultaneously ready periodic and retry triggers cannot produce two attempts at the same logical time.
- Before consuming pending reconciliation state, the coordinator gives an already-ready health-server or caller stop condition priority. Cancellation therefore cannot be followed by a newly started snapshot.

Reconciliation runs synchronously in the coordinator, guaranteeing one attempt at a time. Its Docker snapshot phase uses the fixed ten-second child context defined above. Cancellation reaches Docker operations immediately; filesystem work receives the daemon context and observes cancellation between mutation phases.

### Event-stream recovery

Each event-stream attempt receives its own child context. Closed or failed event channels cancel that child context, become disconnected state, set the Docker event-stream health condition, and start a cancelable reconnect timer. Backoff doubles from one second to a maximum of thirty seconds. It resets and clears the condition only after the stream produces a valid event or remains open for thirty seconds. Merely receiving new channels is not considered a successful connection.

The Docker mapper's terminal error is authoritative over generic channel closure and stream stability. If the event channel closes, the coordinator first consumes any queued error. Before a stability timer clears health or resets backoff, it likewise rechecks queued terminal state. An error buffered before both mapped channels close therefore remains the diagnostic and cannot be misclassified as a stable stream.

### Shutdown

`Run` derives one child context from its caller and owns its cancel function. Caller cancellation or unexpected health-server termination cancels that child context. Cancellation stops every timer, invokes the current event-stream cancel function, reaches in-flight Docker work, and prevents another reconciliation. Caller cancellation, including the signal context used for SIGINT and SIGTERM, is an expected stop condition rather than an initiating run error.

After the health server starts, one daemon-owned watcher selects only `HealthServer.Done` and the daemon context. Health completion makes the watcher call the daemon cancel function; daemon cancellation makes it exit. The watcher never schedules work and `Run` joins it before entering cleanup or returning, which lets health termination interrupt a synchronous reconciliation without weakening terminal-error classification.

Cleanup records whether `HealthServer.Done` was already closed, then calls
`HealthServer.Shutdown` with a fresh five-second context. Regardless of the
shutdown result, cleanup waits unconditionally for `Done` before reading
`HealthServer.Err` and before calling `NetworkSource.Close`. A completion that
predates the shutdown call is unexpected even when `Err` is nil; a nil
completion caused by daemon-requested shutdown is normal. After normal caller
cancellation, `Run` returns `nil` when cleanup succeeds. Unexpected
health-server termination remains an initiating error. `Run` joins that
initiating error, any terminal serve error not already captured, shutdown
error, and Docker close error so no cleanup failure is hidden and no serve
error is duplicated. No debounced callback, stream context, or server
goroutine may outlive `Run`.

## Health Model

The tracker stores active conditions keyed by concern and a maximum of ten history records. Concern-to-wire mappings are fixed:

| Concern | `error_type` | `severity` | Cleared by |
|---|---|---|---|
| Docker snapshot | `docker` | `major` | A complete successful snapshot |
| Docker event stream | `docker_events` | `minor` | A valid event or thirty stable seconds |
| Hosts apply | `update` | `major` | A successful `HostStore.Apply` |
| Hosts preparation or recovery | `validation` | `critical` | A successful `HostStore.Prepare` |

A failure replaces the active record for its concern and appends a new history record with a unique internal ID. Repeated failure leaves earlier records in history but only the newest record is active. Success removes the active condition without deleting history.

History eviction removes the oldest record not referenced by an active condition. With four defined concerns and a ten-record bound, the latest record for every active condition remains available in the response. History is diagnostic and never controls current health.

The handler copies active conditions and history into one immutable snapshot while holding the tracker lock and performs JSON rendering after unlocking. It never reads live maps or slices outside the lock.

The response schema is:

| Field | Presence | Meaning |
|---|---|---|
| `healthy` | Always | `true` only when no active condition exists |
| `status` | Always | `ok` when healthy, otherwise `degraded` |
| `message` | Always | `No errors recorded`, `All active conditions recovered`, or `System degraded: N active condition(s)` |
| `error_count` | Always | Number of retained history records, not active-condition count |
| `errors` | Always | Retained history in oldest-to-newest order |
| `reason` | Degraded only | Message from the newest active condition |
| `time_until_healthy` | Degraded only | Literal string `unknown`; recovery requires observed success |

Every entry in `errors` always contains `timestamp`, `message`, `error_type`, `severity`, `recovery_period`, and `time_until_recovered`. Timestamps use Go's standard JSON encoding for `time.Time`. The record currently referenced by an active condition reports `unknown` for both recovery fields. Superseded or cleared records report `0s` for both fields. No timer silently converts an unresolved condition to healthy.

Transition examples are normative:

1. With no history, the endpoint is HTTP 200 with `error_count: 0` and `message: "No errors recorded"`.
2. One snapshot failure appends one `docker` record, makes it active, and returns HTTP 503 with `error_count: 1`, `reason` equal to that failure message, and both duration fields `unknown`.
3. A repeated snapshot failure appends a second record, supersedes the first to `0s`, and keeps only the second record active with `unknown` fields.
4. A successful snapshot clears the active condition, returns HTTP 200 with both historical records retained, and reports `message: "All active conditions recovered"`.
5. After more than ten failures, the oldest non-active records are evicted while each latest active record remains pinned.

The HTTP server configures read-header, read, write, idle, and shutdown timeouts. Listener creation is synchronous so an invalid or occupied address fails startup instead of creating an unreachable self-reported error.

Timeouts are fixed internal constants: five seconds for read headers, ten seconds for request reads, ten seconds for response writes, sixty seconds for idle connections, and five seconds for graceful shutdown. They are not CLI options.

An unexpected serve error after startup cancels the coordinator and is returned from `Run`; the process supervisor, rather than an unreachable health endpoint, owns restart. Normal `http.ErrServerClosed` shutdown is not an error.

## CLI Construction

Commands are constructed with fresh Cobra factory functions. Package-level commands and mutable flag variables are removed.

`main` creates a signal-aware context and calls `ExecuteContext`. The root command sets `SilenceUsage` and `SilenceErrors`; `main` writes one returned error to stderr and chooses the exit status.

The build-injected `version` variable remains in package `main` and is passed into the command factory, preserving the existing `-X main.version=...` build contract. Modules return contextual errors and log only when an operation is intentionally continued; the outer command boundary prints terminal errors once.

Command tests inject run and regenerate functions and execute the complete root command in memory. Business modules do not import Cobra.

`--networks/-n` retains its existing comma-separated string syntax. The command layer splits, trims, validates, and deduplicates it before resolving `--default-network`. It does not require an updated Saltbox template. The version template is pinned and tested as `sdhm version <version>` rather than relying on an incidental Cobra default.

Duration parsing first uses `time.ParseDuration`. If that fails, an exact positive base-10 integer followed by `d` is converted to 24-hour days with overflow checking.

## Go 1.27

`go.mod` changes to `go 1.27.0`. GitHub Actions continues to use `actions/setup-go` with `go-version-file: go.mod`.

The rewrite may use Go 1.27 standard-library facilities such as `net/netip`, `slices`, `maps`, `errors.Join`, `sync.WaitGroup.Go`, `testing/synctest`, and modern `net/http` routing. It does not add compatibility shims for older Go versions.

## Test Strategy

Every production behavior is introduced through a failing test, observed failing for the intended reason, then implemented minimally and refactored while green.

### Command tests

- Fresh command tree and isolated output per case.
- Valid and invalid durations, ports, paths, section names, and network flags.
- Existing comma-separated `--networks/-n` parsing, trimming, empty-item filtering, order-preserving deduplication, and all-empty rejection.
- Explicit, Saltbox-preferred, and first-network fallback resolution for `--default-network`.
- Rejection of an explicit default network absent from the normalized monitored list.
- Exact historical Saltbox invocation and three-token version output.
- Context propagation, version output, and concise runtime errors.
- Signal-context cancellation producing a clean exit without stderr output.

### Docker tests

- Complete combined snapshots through a fake minimal Moby interface.
- One list call with all network filter values, one inspect per listed container, and list/inspect error propagation.
- Canonical not-found inspect races being skipped while every other inspect failure aborts the snapshot.
- Multiple endpoints per container, empty-network contributions, malformed endpoint rejection, IPv4/IPv6 selection, `Aliases`-only naming, sorting, and multi-network event filters.

### Hosts tests

- Exact marker recognition, duplicates, missing markers, reversed markers, CRLF, and marker-like substrings.
- Stable rendering and byte preservation outside the managed section.
- Default-network bare-plus-qualified names and secondary-network qualified-only names.
- No-change behavior.
- Valid recovery and fail-closed invalid recovery.
- Adjacent temporary paths, sync/rename failure behavior, detached bounded rollback after caller cancellation, complete mode-bit preservation, ownership/write/final-mode ordering, and regeneration backup metadata.

### Daemon tests

- Initial reconciliation and retry after initial failure.
- Debounce, maximum delay, periodic timing, and event coalescing.
- Exponential reconnect progression and stability reset.
- Failed reconciliation preserving current hosts state.
- Health condition activation and clearing.
- Cancellation during Docker work and complete shutdown joining.
- Caller cancellation producing a clean `nil` result when shutdown succeeds.
- Unexpected server termination and cleanup failures producing non-nil joined errors.

Time tests use `testing/synctest` or explicit synchronization, never timing sleeps.

### Health tests

- Compatible fields and status codes.
- Active-condition lifecycle and bounded history.
- Concurrent condition updates and HTTP rendering under the race detector.
- HTTP listener startup failure and graceful shutdown.

### Repository gates

The Makefile provides non-mutating `fmt-check`, `tidy-check`, `test-race`, and `check` targets. `fmt-check` fails when `gofmt -d` emits output. `tidy-check` runs `go mod tidy -diff` and never rewrites module files. `check` runs those targets, tests with the race detector, vet, and build. CI runs `make check` before cross-compilation. Workflow permissions default to `contents: read`; only the release job overrides that permission with `contents: write`.

Coverage is reported for review, but no arbitrary percentage substitutes for the required behavioral cases.

## Disposable-VM Acceptance

The lifecycle coordinator uses the `saltbox_vm` MCP workflow and a current supported Ubuntu core-profile guest. The exact helper-returned `guest_instance_id` fences every guest call.

Acceptance performs these operations without touching the guest's production `/etc/hosts`:

1. Build or transfer the Go 1.27 binary.
2. Run `docker network inspect saltbox` as a preflight. If the core guest does not already contain the Saltbox-provisioned network, fail acceptance and preserve the guest for diagnosis; do not create a substitute network.
3. Create `/tmp/sdhm-acceptance/hosts` with ordinary localhost content and use `/tmp/sdhm-acceptance/hosts.backup` as its backup.
4. Create a disposable secondary network named `sdhm-extra`; this supplements rather than substitutes for the real Saltbox network.
5. Run with `--networks saltbox,sdhm-extra`, `--interval 1s`, `--debounce-delay 100ms`, `--debounce-max-delay 500ms`, and a loopback health listener on port 18080. Omit `--default-network` to exercise Saltbox-compatible automatic resolution.
6. Attach one disposable container to both networks with a known alias. Verify the Saltbox IP receives `alias alias.saltbox` and the secondary IP receives only `alias.sdhm-extra`.
7. Stop the first daemon and verify bounded shutdown. Start a second daemon on isolated `hosts-fallback`, `backup-fallback`, and port 18081 using only `--networks sdhm-extra`; verify first-network fallback provides `alias alias.sdhm-extra`, then stop it cleanly.
8. Start a third daemon on isolated `hosts-explicit`, `backup-explicit`, and port 18082 using both networks and `--default-network sdhm-extra`; verify the bare alias moves to the secondary endpoint, then stop it cleanly. Restart the first daemon before continuing the event, failure, recovery, and shutdown checks below.
9. Disconnect and reconnect the first container on each network and verify debounced combined updates.
10. Record the temporary hosts-file hash, stop Docker, wait for a failed reconciliation, verify the hash is unchanged and health is degraded, restart Docker, and verify reconciliation and health recover.
11. Corrupt marker ordering, restart, and verify validated backup restoration.
12. Query healthy, degraded, and recovered HTTP responses.
13. Send SIGTERM and verify bounded clean shutdown with no later file mutation.

The guest is destroyed after success. A failed guest is stopped and preserved only while its state is needed for diagnosis, following the workspace VM coordination rules.

## Replacement Sequence

1. Record characterization tests for the supported external contract.
2. Introduce the new command, daemon, Docker, hosts, and health modules test-first.
3. Exercise the new daemon with fake Docker and temporary files.
4. Switch `cmd/sdhm` wiring to the replacement.
5. Remove the superseded `internal` packages and obsolete tests.
